# Arena — Legacy → src/ Migration Progress

Durable tracker for the incremental "strangler fig" migration of
`arena-campeonatos-v2-intervencao-19.html` (still shipped to production via
`scripts/prepare-legacy.mjs`) into the modular `src/` Vite app. Source of
truth for what's actually landed on `main` — conversation memory does not
survive compaction, this file does.

Mode: autonomous. User has authorized executing every phase to completion,
always taking the recommended path, without stopping to ask — see decision
log below. Only stop for a genuine blocker.

## How each phase runs

1. Write/refresh the phase's plan under `docs/superpowers/plans/` (writing-plans skill).
2. `EnterWorktree`, then immediately `git merge main --ff-only` (worktrees branch from `origin/main`, not local `main` — see the decision log entry below).
3. Execute via `superpowers:subagent-driven-development`: implementer → task review → (fix loop) per task, ledger at `.superpowers/sdd/progress.md` inside the worktree. Every new/changed `class="..."` gets checked against `layout.css`/`tokens.css` for both the class's own rule and any `<class> <child-selector>` rule — see "Process note" below.
4. Final whole-branch review (opus) → fix Critical/Important → re-review.
5. `npm test && npm run build && npm run verify` green on the merged result.
6. Merge to `main` locally (recommended default, established Phase 1), delete branch, clean up worktree.
7. Update this file.

## Known follow-ups (not bugs, deliberately deferred — surfaced by Phase 2a's final review)

- **Public portal, PDF export, and registration-approval only see the *active* category.** Root-mirroring (`state.teams`/`state.matches`) means `public-championship.js`, `services/pdf.js`, and the registration-approval handler in `championship.js` all read/write whichever category was active at last save — switch categories and save anything, and the public link's team/match list silently changes to the new active category (the full data isn't lost — it's all still in `state.categories` — just not what these three surfaces currently read). Not urgent: `src/` isn't the live production surface yet (`scripts/prepare-legacy.mjs` still ships the legacy monolith). Must be resolved before Phase 7 (build cutover) — either by making these three surfaces category-aware, or by an explicit product decision that they intentionally show "whichever category was last active."
- **Registration approvals have no way to pick which category a new team joins** — same root cause as above.
- Cosmetic, low-priority: `addCategory`'s default name (`Categoria ${length+1}`) can repeat after a remove-then-add cycle (ids stay unique, so no functional bug); `ordem` field is written but nothing reads it yet (dormant until Phase 2d's phase ordering needs it); category audit log entries don't name which category was added/renamed/removed.
- Pre-existing, predates Phase 2a, not introduced by it: `[data-pdf]`/`[data-publication]` in `championship.js`'s `bind()` use `addEventListener` on nodes that live outside the re-rendered `content` section and are never cleaned up, so listeners accumulate one per `render()` call. `[data-remove-team]` filters `state.teams` without fixing up the numeric `match.home`/`match.away` indices in `state.matches`, corrupting any already-generated fixture list when a team is removed after fixtures exist. Worth a small fix-it pass (own plan, not blocking) before Phase 3b (Matches & scoring) builds more on top of the match/team relationship.

## Known follow-ups — Phase 2b (Teams & Roster)

- **Image payload strategy needs revisiting before Phase 5.** `compressPhoto` stores photos as base64 data URIs directly in the Firestore document (a faithful legacy port, not a new risk on its own) — but combined with category root-mirroring, each photo is now duplicated across `state.teams` and `state.categories[].teams`, and the whole state re-serializes on every save. A few dozen photographed athletes can approach Firestore's 1 MiB per-document limit. Phase 5 (branding/sponsors) adds more images via `readAndResizeImage` — worth switching to Firebase Storage + URL references before that lands, rather than compounding the same pattern a second time.
- `roster.js`'s `athleteById`/`athName`/`teamNameById` are ported and tested but have no caller yet in `src/` — they're the read-side helpers Phase 3 (match events, disciplinary views) will need. Not dead code, just early.
- `class="btn ghost sm"` (`championship.js`, roster modal) has no `.sm` CSS rule anywhere in `src/styles/` — pre-existing gap (already used elsewhere before this phase), same class of bug `.row` was in Task 2 before its fix. Worth a sweep for every `class="..."` in `src/pages/*` with no matching selector, rather than fixing them one at a time as each is noticed.
- `persist()` (in `championship.js`) now catches a failed `saveChampionship` and toasts it, but callers still proceed to write an `addAudit(...)` entry for a change that was never actually saved (a log-accuracy gap, not data loss — the in-memory state is intact for a retry). Fix belongs with a broader look at `persist()`'s callers, not a one-line patch.
- `categoriesView()`'s category row (2-3 children) now sits in the same 4-column `.team-row` grid the roster UI needed; the unused 4th track shifts its "Remover" button ~10px from where it sat before. Cosmetic only.
- `updateAthlete`'s `dob`/`numero` fields accept only strings (`(dob || '').trim()`-style coercion) — fine for every current DOM-sourced caller, but worth a guard if a future non-DOM caller (e.g. a bulk-import feature) ever passes a number or Date.

Fixed same-session in `7c5bc8e` (test-fixture-only fix, no production code changed) before Task 3's review closed. Lesson for 3a/3c, who will keep touching this same root/phase seam: `generateActivePhase` now carries a comment at its `saveRootIntoActive(state)` call explaining the invariant.
- **Whole-branch review caught two scope gaps the per-task reviews couldn't see** (both fixed before merge, commit `11d8688`): `new-championship.js`'s creation wizard still offered a `mata` format option that led to a dead end once selected (no matching Fases-tab option, `generateActivePhase` refuses it) — removed. `phase.cfg.nGrupos`/`turnos` had no editor anywhere, hardwiring every phase to 2 groups/single-turno — added number inputs to the phase row in `fasesView()`.

Real DRY gap now that both call sites exist — exporting `blankPhase` and reusing it would be a low-risk one-line fix. Deferred, not blocking.
- `progressionSummary(category, phase)` has no null-guard on `phase` (unlike `saveRootIntoPhase`, which does). Safe today — the only call site (`fasesView()`) always passes a real phase — but worth a guard if a future caller passes a possibly-undefined one.

Cosmetic; Phase 3c (which builds the actual classification logic) is the natural place to decide the right behavior here.
- `standings()` (`championship.js`) merges all matches into one flat table regardless of `match.grupo` — correct for `liga`/pre-2d, silently wrong for a `grupos`/`gxg` phase (multiple groups shown as one table). Real per-group standings is Phase 3c's job (`computeStandings`/`standingsTable`); this phase makes multi-group phases *reachable* without making them *correctly displayed* yet.
- The championship header's format badge (`state.formato.toUpperCase()`) is written once in `mount()` and never refreshed after a phase switch or format change — goes stale. Pre-existing pattern (header built once, not re-rendered), not introduced by this phase, just newly visible now that format can change without a full page reload.
- `venueById`/`officialById` (2c) and `roster.js`'s read-helpers (2b) remain uncalled — still waiting on Phase 3b (match scheduling/events).

## Known follow-ups — Phase 3a (Draw & Bracket Engine)

- **Fixed a latent legacy bug, not a regression:** legacy's `phaseComplete`/`qualifiedFromPhase` called a function named `winnerOf` that was never defined anywhere in the 12,000-line monolith (confirmed by exhaustive grep) — a dead `ReferenceError` path if either branch had ever been reached in production. This phase defines `winnerOf` properly in `engine.js`; `phases.js`'s `phaseComplete` inlines the equivalent one-line check instead of importing it, to avoid a circular dependency (`engine.js` already imports from `phases.js`).
- **Two real correctness bugs were found and fixed during this phase's own review loop** (not shipped broken — surfaced before merge): (1) `resolveTie`/`advanceBracket` initially conflated a genuine construction-time bye with a mid-tournament pending slot, crowning premature winners; the fix's first pass then regressed non-power-of-two brackets (5,6,9-14 teams) into being permanently unfinishable, caught by the final whole-branch review and fixed with structural bye detection, then a second review round found the fix needed 2+ `advanceBracket` calls to converge a multi-round bye cascade (n=9/10), fixed by restructuring into a single topological pass. (2) A pre-existing bug from Phase 2d — `[data-phase-turnos]`/`[data-phase-ngrupos]` handlers mutating `phase.cfg` directly, silently clobbered by `persist()`'s root→phase sync whenever editing the *active* phase — was caught here (while fixing the same-shaped bug in this phase's new mao-unica/terceiro toggles) and fixed for all four handlers. See the plan's task-review history for full traces.
- **No regression test locks in single-call bracket-advancement convergence** — the sweep test (`engine.test.js`, "every team count from 2 to 16 can reach a champion") loops `advanceBracket` until quiescence, so it would stay green even if the single-pass fix were reverted to the old two-phase relaxation. Cheap to add (snapshot before/after a second call, assert no change) — not done here, flagged by the final review as test debt rather than a live defect.
- **Already-persisted brackets for n ∈ {5,6,9,10,11,12} created before this phase's fixes may have a permanently-stuck third-place tie** (one side `null` forever, from before the `ids.length > size * 3/4` gate existed). Regenerating the phase (`Gerar/Refazer`) clears it — not a live-data migration concern since `src/` isn't the production surface yet, same status as every other Phase 2/3a follow-up.
- The "3º lugar" checkbox in Fases stays checked/enabled even for team counts where no third-place match can structurally exist (the setting silently has no effect at generation time for those counts). Cosmetic.
- `standings()` (Tabela tab) shows an all-zero table for a `mata` phase — it reads `state.matches`, which mata phases never populate (all data lives in `state.bracket`). `games()`/`config()` grew a one-line redirect note for `mata`; `standings()` doesn't have an equivalent yet. Same class of gap Phase 2d already left for `grupos`/`gxg` (no per-group standings) — real fix is Phase 3c's `computeStandings`/`standingsTable`.
- A championship created via the wizard with `formato:'mata'` gets no `cfg.maoUnica` set, so its first phase defaults to two-legged ties (four score boxes) rather than single-leg — faithful to legacy's own default, but worth a UX look (default `maoUnica:true` in the wizard) if two-legged surprises organizers.
- `renderMataFromGroups` and `qualifiedFromPhase`'s `mata` branch remain deferred to Phase 3c (need `computeStandings` for the groups-phase classification half of that pipeline, same reasoning as Phase 2d's `applyProgression` deferral) — now buildable correctly once 3c lands, since `winnerOf` and a real `bracket.rounds` shape exist.

## Known follow-ups — Phase 3b (Matches & scoring)

- **Fixed a latent legacy bug, not a regression:** `splitInfo`'s dead fallback line (a self-contradicting expression that only ever evaluated to `''` or `undefined`) was simplified to `parts.slice(2).join(' · ') || ''`.
- **Whole-branch review found 4 Important + 2 Minor issues, all fixed before merge** (fix commit `e8c8cbe`, re-reviewed): (1) the `[data-score]` instant-save handler called `render()` right after `persist()`, destroying the score grid mid-use — a real data-loss bug, `render()` removed. (2) `saveMatchOps` never cleared `meta.venueText` (the one-time legacy free-text migration field), so explicitly clearing a match's venue in the ops modal left the stale legacy text showing via `metaLine`'s fallback — fixed by clearing `venueText` alongside `venueId`. (3) legacy BR-formatted dates (`dd/mm/yyyy`) migrating from `match.info` were assigned raw into `meta.date`, corrupting `<input type="date">`; added `toISODate()` to convert (and safely no-op on garbage) before assignment. (4) the two new `addAudit` calls for score/match-ops updates omitted `before`/`after`, breaking the audit trail's data — both now pass `result.before`/`result.after`. Minor: dropped double-`esc()`-escaping on audit summary team names (convention is raw-store, escape-at-render); `clearResults` now calls `advanceBracket` after resetting bracket ties so a persisted bracket doesn't sit stale until the next Chaveamento render.
- **Re-review found the venueText fix's own regression test was weak** (round-tripped through a freshly-generated single-segment `match.info` that never populated `venueText` in the first place, so it passed with or without the fix) — rewritten (`e66adf6`) to seed a real `·`-delimited legacy `info` string so `matchMeta`'s migration genuinely backfills `venueText` before the clear is asserted; verified by hand that the strengthened test fails when the fix line is reverted.
- `clearResults` doesn't reset `meta.status` (a match cleared of its score still shows `status: 'live'`/`'finished'` if the ops modal had set one) — cosmetic, no data-loss, worth revisiting alongside Phase 4's match-events work.
- `clearResults` empties `match.scorers` but Phase 4's disciplinary/events model may introduce a richer `events` field on matches; when that lands, `clearResults` should be revisited to reset whatever superset field replaces `scorers`.
- Legacy free-text `venueText`/malformed-date edge cases (info strings that don't match the `dd/mm/yyyy · hh:mm · local` shape at all) degrade gracefully (empty fields) rather than erroring, but aren't exhaustively tested beyond the one garbage-date case — acceptable given `src/` isn't the production surface yet.

## Process note: the class/CSS mismatch bug, three times running

Phase 2b (`.row` used with no CSS rule; `.team-row` overflowing a 5-child athlete row) and Phase 2c (`.team-row` overflowing a 4-child staff row; then the fix's replacement `.row` having no input styling) all shipped the same root cause: markup written against a CSS class without checking what that class's rule — or its children's rule — actually does. Every instance was only caught by the whole-branch review, never the task-level one. **Standing instruction from Phase 2d onward:** for every new or changed `class="..."` in a diff, grep `layout.css`/`tokens.css` for that exact class **and** for `<that-class> <child-selector>` rules (e.g. `.row input`, not just `.row`) before considering the task done — both at implementer self-review and at task-review time, not deferred to the final pass.
